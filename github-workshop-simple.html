Git vs GitHub

The one distinction to remember

GIT

The tool on your computer

  • Records every change
  • Saves checkpoints (commits)
  • Lets you compare and go back
GITHUB

The place your team shares it

  • Hosts the project online
  • Pull Requests and reviews
  • Issues and automated checks

Git tracks the changes. GitHub is where the team works together around them.

The whole workflow in one picture

Branch → Commit → Push → Pull Request → Review + Checks → main

The rest of the workshop just walks through this line, one step at a time.

Step 1 · Start tracking changes

Turn a normal folder into a Git project

git init          # start tracking this folder
git add .         # stage your files
git commit -m "Initial project setup"

A commit is a saved checkpoint. You can always come back to it.

Write commit messages people understand

NOT HELPFUL

git commit -m "stuff"

Nobody knows what changed.

HELPFUL

git commit -m "Add baseline churn model"

Answers the question: what changed?

Read the history

Anyone should be able to see what happened

git log --oneline
a91f4d2 Add baseline churn model
31c72a1 Initial project setup

Look at a specific change:

git show a91f4d2

Step 2 · Put it on GitHub

Send your local project to the shared repository

  https://github.com/YOUR-ORG/churn-project.git

🧪 Quick check

Which command makes a new branch AND switches to it?

A   git branch feature/model

B   git switch -c feature/model

C   git checkout main

D   git push origin main

Reveal answer

B. It creates the branch and moves you onto it in one step.

Step 4 · Pull Requests

A Pull Request is where the team reviews your change

feature/model → Pull Request → main

AUTHOR

Explains the change.

REVIEWER

Asks questions, suggests fixes.

CHECKS

Run automatically.

The point isn’t clicking “merge” — it’s the shared review before the change reaches main.

Merge conflicts

Git can spot a clash. It can’t decide who’s right.

Two people change the same line:

threshold = 0.50     # yours
threshold = 0.65     # theirs

Git shows both and asks you to choose:

<<<<<<< HEAD
threshold = 0.50
=======
threshold = 0.65
>>>>>>> feature/model

You pick the right value, edit the file, then git add and git commit.

Don’t commit everything

Use a .gitignore file

data/
.env
credentials.json
__pycache__/
.ipynb_checkpoints/
KEEP OUT

Secrets, large data, and generated files.

REMEMBER

GitHub is for collaboration — not for publishing sensitive data.

Automated checks (CI)

What if every Pull Request tested itself?

Pull Request → GitHub Actions → Tests run → Merge

A small file turns this on:

# .github/workflows/tests.yml
name: Tests
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest

When a check fails

PASS

Keep reviewing and merge when ready.

FAIL

Investigate and fix the branch before merging.

A failing check is an early warning that something may be broken.
